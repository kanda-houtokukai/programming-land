## §0. このセッションの役割

**これは実装セッションではない。監査セッションである。**

このプロジェクトは Chat（設計・検証）と Code（実装）の二人三脚で進んできたが、**不具合の多くを発見してきたのは神田さん（ユーザー）**だった。つまり Chat と Code の両方が見落としている領域がある。

**あなたの仕事は、その見落としを外から見つけることだけ。**

### 0-2. ★絶対に守ること

- **コードを1行も変更しない。** 修正案は書いてよいが、実装はしない
- **`npm run deploy` を実行しない**
- **`--update` を実行しない**（`npm run verify` の実行は可）
- **`main` に push してよいのは、最後の監査報告書1ファイルだけ**
- 見つけた問題を**直したくなっても直さない**。報告して終わる

### 0-3. ★このセッションは無人で走る（安全装置）

神田さんは席を外している。**確認を求めても誰も答えない。** 自分で自分を止められるようにすること。

**着手時にやること（最初のコマンド）**

```
git rev-parse HEAD          # 起点を記録（59e7d6d のはず）
git status --porcelain      # 空であること。空でなければ何もせず報告して終了
```

**禁止コマンド（絶対に実行しない）**

```
npm run deploy / npm run build
node tools/*.mjs --update
git push --force / git reset --hard / git checkout -- / git clean
rm / mv （リポジトリ内のファイルに対して）
npm install / npm ci        # package-lock.json が動く
```

`npm run verify` は**実行してよい**（読み取りのみ）。ただし FAIL しても**直さない**。FAIL したこと自体を報告する。

**commit の直前に必ずやること**

```
git status --porcelain
```

**報告書1ファイル以外が出ていたら commit しない。** 何が出たかを報告書に書き足して、その1ファイルだけを `git add` する。
`git add -A` や `git add .` を使わない。**ファイル名を明示して add する。**

**迷ったら止まる**

- 「これは変更していいのか」と迷ったら、**変更しない**。報告書に「判断が要る」と書く
- 調べるためにファイルを書き換える必要が出たら、**やらない**。「変更せずには確認できない」と報告する
- 想定外のことが起きたら、**そこで止めて、そこまでの結果で報告書を書く**

**作業を失わないこと**

監査は長い。コンテキストが尽きそうになったら、**その時点までの結果で報告書を書いて push する**。
全部見ようとして何も残さないのが最悪。**7割の報告書 > 0の報告書。**

### 0-4. ★台帳を信じない

`progland-handoff.md`（台帳）と `brushup/` の指示書は、**Chat と Code が書いた主張**であって事実の証明ではない。

- 台帳が「実機OK」と書いていても、**本当に確認されたかは別**
- 指示書が「Chat が確認済み」と書いていても、**その確認が正しかったとは限らない**（実例: 建物PNGの余白について Chat が「加工済み」と書いたが、現物は違っていた）
- 「studio 完全無変化」等の主張は、**git diff で自分で確かめる**

**台帳は「何が主張されているか」を知るために読み、その主張を現物と突き合わせる。**

### 0-5. コンテキストを節約する

台帳は約35,000字ある。全文を漫然と読むと、それだけで容量を使い切る。

- **`grep` / `sed` / スクリプトで必要箇所だけ取る**。ファイル全文を `view` しない
- **ブラウザは使わない**。この監査は静的解析で行う（動かさないと分からないものは「要実機確認」として報告する）
- 大きいファイルは構造だけ把握してから該当箇所へ

## §1. 何を確かめるか

以下は**出発点**であって、これだけやればよいという意味ではない。**気になったことは自分の判断で追ってよい。**

### 1-1. データの整合

- `DEFS` の全型が、`PALORDER` / `GAMELAB_PALORDER` のどちらかに載っているか。**どこにも出ないカードはないか**
- `DEFS` の全型に**アイコンと `desc`（せつめい文）があるか**。抜けはないか
- `brushup/cards-reference.md` が `DEFS` と一致しているか（`gen-cards --check` が通るかだけでなく、**中身が実態と合っているか**）
- みほん（gamelab 6本・studio 4本）が**使っているカードがすべて実在**するか
- みほんの `gameConfig` と中身が噛み合っているか（クリア=スコアなのに得点手段がない等）
- `tools/studio-baseline.json` が記録している値と現行コードが一致しているか

### 1-2. verify が見ていない領域（★ここが本丸）

**`npm run verify` が全PASSしても検出できないもの**を洗う。過去に実際すり抜けた種類:

- **id と画像の対応**（アイコン29枚・カバー絵10枚が正しい型／みほんに付いているか）。**入れ替わっていてもテストは通る**
- **見た目の寸法**（余白・縦横比・viewBox の整合）。実際に `gamelab-building.png` が既存規約と違う余白で1度入った
- **実行時エラー**（TDZ 等）。node の verify では拾えない
- **CSS と JS の食い違い**（実例: `.pill` の `box-sizing` と `cardW()` の見積もりが12pxずれていた）
- **SVG の要素サイズと viewBox の食い違い**（実例: 全カードが 93〜97% に縮小されていた。長期間誰も気づかなかった）

**同種の食い違いが他にも残っていないかを、機械的に洗ってほしい。**
たとえば: 幅や高さを JS 側で計算している箇所と、対応する CSS の値が合っているか。SVG を描いている他の箇所に同じ viewBox の不整合がないか。

### 1-3. 実機確認の履歴

- 台帳の各版に「実機OK」「実機確認待ち」が記録されている。**⚠️実機確認待ちのまま残っている版はないか**
- 台帳に「通しの実機確認は `brushup/cards-reference.md`（機能一覧）が揃ってからまとめて実施」という方針が書かれている。
  **`cards-reference.md` は b6e で既にできている。その通し確認は実施されたのか、記録があるか**
- 「簡易確認で合格」とされた版が、後で通し確認されたのか
- **実機でしか確認できない項目が、実機ゲートに書かれたまま確認記録がないもの**を一覧にする

### 1-4. 「変えない」と宣言したものが本当に変わっていないか

各指示書には §「変えないもの」がある。**主張と現物を突き合わせる。**

特に:

- **studio 完全無変化**（`src/studio/`・`PALORDER` 18種・`ACTOR_K` 2.2・`STUDIO_GUIDE`・studio の内観・アイコン01〜18）
- **凍結ベースライン**（トレース732イベント・パス98本）が、各版で本当に不変だったか
- `G.SNAP = 78`・`CFG.MOVE_MS = 340`・`TICK = 400`・`OP_MS = 100` などの手触り定数

`git log` を使って、**宣言に反する変更が混入した版がないか**を追う。

### 1-5. 死んだコード・未使用アセット

- **使われていない import・変数・関数**（暫定SVGグリフの残骸など）
- **参照されていない画像/音声ファイル**が `src/assets/` に残っていないか
- **到達しないコード**（条件が常に偽になる分岐など）
- ガイドの `title` は `ParentGuide.jsx` で描画されていない（17件が死にデータ）。**同種の「持っているが使っていないデータ」が他にないか**

### 1-6. 保存データと移行

- `SCHEMA_VERSION` は 8。**旧セーブ（7以前）が壊れずに読めるか**をコードで追う
- `gamelab.milestones` が無い旧セーブでの挙動
- **ぶたいのショップ連動（b6m）で、未所持の背景を使った既存作品が壊れないか**（救済ロジックの穴）
- `bump` は gamelab のこうぐだなから外したがエンジンは解釈し続ける。**`bump` を使った既存の gamelab 作品が今も動くか**

### 1-7. リリース前に消し忘れそうなもの

- **`#gamelab-dev` の開発用バックドア**が本番に残っている。意図的か、消し忘れか
- デバッグ用のコード・ログ・`window.__` 等の残骸
- 実験用のファイルが `src/` に残っていないか

### 1-8. 未完了タスクの棚卸し

台帳の「未完了タスク」を1つずつ見て、**本当にまだ生きているか**を判定する。

- 後続の版で実質的に解決されているのに残っているもの
- 逆に、**完了扱いになっているが実は終わっていないもの**

### 1-9. 放置されている判断待ち

Chat が「判断が要る」と提起したまま、**決まっていない／忘れられているもの**を洗い出す。

既知のもの（他にもあるはず）:

- **背景の方針**（案あ 遠景＋床2層／案い 新規生成／案う 無地）が未決のまま
- **ゲームのせってい再設計**（設計とモックはあるが未実装。縦予算が当時より悪化している）
- **カードのせつめいに動きのアニメーションを付ける案**
- 段階3の `clone`（ぶんしんを だす）＝ **カード29種の最後の1枚が未実装**

## §2. 報告のしかた

### 2-1. 報告書を1本作る

`brushup/audit-report-2026-07-25.md` として書き、**それだけを push する**（他のファイルは触らない）。

### 2-2. 重大度で分ける

| 区分 | 意味 |
|---|---|
| **A: 壊れている** | いま実際に不具合が起きている。子どもが触ると困る |
| **B: 壊れる可能性** | 条件が揃うと壊れる。移行・エッジケース・依存の食い違い |
| **C: 整合していない** | 動くが、記録と実態が違う。次に読む人が誤解する |
| **D: 確認漏れ** | 誰も実機で見ていない。動くかどうか不明 |
| **E: 放置されている判断** | 決まっていないまま忘れられている |

### 2-3. 各項目に必ず書くこと

- **何が問題か**（1〜2行）
- **どうやって確かめたか**（コマンド・ファイル・行番号。**「〜のはず」で書かない**）
- **影響**（誰が・いつ困るか）
- **直し方の案**（実装はしない）

### 2-4. 見つからなかったことも書く

「調べたが問題なかった」も価値がある。**確かめた範囲**を明記すること。
そうしないと、次に読む人が「調べていない」のか「調べて問題なかった」のか区別できない。

### 2-5. 自信の度合いを書く

推測が混じる場合は**そう明記する**。確実な事実と推測を混ぜないこと。
このプロジェクトでは、Chat が推測を断定で書いて実装を誤らせた例が複数ある。

## §3. やらないこと

- **コードの修正**（`src/` `tools/` `docs/` を1バイトも変更しない）
- **deploy・版上げ・台帳の更新**
- **`--update`**
- **ブラウザでの動作確認**（静的解析で行う。動かさないと分からないものは D 区分で報告）
- **報告書以外のファイルの push**
- 問題を見つけて**その場で直すこと**（報告して終わる）
- **`git add -A` / `git add .`**（ファイル名を明示して add する）
- **`npm install` / `npm ci`**（`package-lock.json` が動く）
- 調べるために**一時的にファイルを書き換えること**（「変更せずには確認できない」と報告する）

> ⚠️ **無人で走っている。** 迷ったら実行しない。止まって報告書に書くのが正解。
> このセッションで壊したものは、誰も気づかないまま次のセッションに引き継がれる。

## §4. 進め方の目安

1. まず `CLAUDE.md` と台帳の**構造**を把握（全文は読まない）
2. `§1-1 データの整合` からスクリプトで機械的に洗う（ここが一番安く広く取れる）
3. `§1-2 verify が見ていない領域` に時間をかける（**ここが本丸**）
4. `§1-4` を `git log` で追う
5. 残りを順に
6. 報告書を書いて push

**時間とコンテキストが尽きそうになったら、そこまでの結果で報告書を書くこと。**
中途半端でも「どこまで見たか」が書いてあれば次につながる。全部見ようとして何も残さないのが最悪。
